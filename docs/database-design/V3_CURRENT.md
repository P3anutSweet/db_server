# 当前订单结构 V3

当前为V3.2七表结构（2026-10-21）。本文件替代 V1/V2 及V3初版的实施建议。V2 中的仓库、包装、退回、分配和过账流程已取消，不能重建。
当前结构以服务器回读快照 [teable-model-v3.json](../../schema/teable-model-v3.json) 为准。

## 日常入口

- **订单明细**：市场、业务负责人、客户、SKU、真实下单日期、订单批次、两套状态、数量、美元单价与总价、跟进记录。
- **月度总览**：按月份、地区市场、SKU汇总业务预测数量、实际订单数量、未提货数量、已提货数量，以及产品、美元单价、预测估值、订单总价。
- 其他活动表：订单批次、产品SKU、客户档案、地区市场、标签字典，共7张。
- 地区市场包含业务大区单选、国家码、业务负责人及隐藏的序号保留上限；无独立大区表。
- 客户档案直接关联偏好标签并记录说明；产品SKU直接关联产品标签并记录依据，两者共用标签字典。
- 产品具有文本EAN字段，保留前导零；完整产品主表尚未导入，未知EAN不自动填写。
- 订单批次用于跨月、跨SKU分组，名称可以重复。
- 原始台账行、导入文件信息、缓存/公式和参考交付计划已嵌入订单隐藏字段，通过“原始资料”视图追溯。
- 来源字段与技术字段在日常视图中隐藏，不需要日常填写。

## 编号和批次

每条SKU订单明细有一个订单号，例如 `SA20261020BRA000001`。
日期只能是真实下单日期。末尾6位按国家连续递增，不按日期、月份或批次重置。
代码：BRA/ARG属SA；VIE/PHI/HKG属SEA；POL/TUR属EU。这里采用业务分组，不作为地理分类。

订单号是只读公式，取已保留的编号前缀和国家序号。后台使用SQLite事务、国家序号唯一约束、记录预约，
并把上限写回地区市场。删除订单不回收序号；失败重试沿用预约。国家或日期变化会提示人工确认，不静默改号。
不要编辑隐藏的编号快照或序号。应用公式与后台校验不是数据库管理员任意修改后的绝对约束。

批次显示名称自动采用“大区码＋批次下单日期YYYYMMDD＋国家码＋总件数”，例如 `SA20261021BRA1250`（格式示例）。
总件数是全部关联SKU订单的当前实际订单数量之和，不使用旧批次文字中的数量或业务预测数量。
总件数变化后，名称随下一次每分钟刷新更新；记录ID不变，名称仍可重复，不作为唯一键。

“批次下单日期”可以明确填写，允许批次包含跨月订单。仅在该字段为空且所有关联订单都有同一个真实日期时自动补入。
缺日期时名称保留“待补日期”；多个订单日期时要求填写批次日期，不自动取最早、最晚或导入日期。
国家冲突、数量缺失或负数均显示命名提示；不将不完整数量作为完整总件数。

历史订单仍按同一市场、相同原批次文字关联到原批次；原文字保留在单独字段。
本次修改只改变批次显示名和汇总字段，不重分组、不改变SKU订单号，也不修改订单真实下单日期。

29条历史订单缺真实日期，按用户要求保留空日期、空订单号，在“日期待补”视图处理。
补齐日期后，后台在下一次刷新生成订单号；不要用导入日、预测月或计划交付日代填。

## 两套状态

渠道业务状态：预测、已下单、客户付款中、提货中、已提货、已交付。

管理状态：需确认订单状态、需确认付款状态、需确认提货状态、需确认交付状态、已完结。

两列独立维护，不因业务选择“已交付”自动标管理“已完结”。旧“已完结”不作为已交付证明。
历史“待提交预测”不直接转换为业务“预测”：已有真实下单日期的记录可初始化为“已下单”，
其余无法确认的业务状态留空，并显示处理提示。管理状态初始为“需确认订单状态”。

## 预测与月度口径

**预测完全来自渠道业务，不是基地预测。** Excel 10月/11月计划列作为2026年业务预测初始化一次，
后续业务直接维护月度总览的业务预测数量和预估单价。原FCST提交日期不是预测数量来源。
预测可以先于订单存在，不需要伪造下单日期或先建订单。

实际数量按真实下单日期（Asia/Shanghai）归组。只有已下单及后续业务状态计入；预测状态排除。
已提货是渠道业务从基地/仓库提走的数量；未提货=实际订单数量-已提货数量。
月度提货显示该月订单的累计提货进度，并非当月发生的提货流水。

某市场仍有非预测订单缺日期或SKU时，该市场各月实际汇总暂留空，并在统计说明显示缺口，
避免把无法归月的数据显示成实际为零；关联订单可检查已登记部分。
价格缺失时金额留空；零单价有效。订单估值逐行四舍五入到美分后汇总；不会只加有价格的订单冒充完整总价。
全表合计可能跳过空值，存在缺口时不能将其解释为完整业务总量。

## 自动化与恢复

`scripts/migrate-minimal-structure.py --apply` 负责从13表迁移到7表：先归档、复制并验证历史，再移至回收站。
七表模式下 `scripts/refresh-order-operations.py --setup` 仅重新配置保留表的视图，不恢复退休模块。
日常运行不带 `--setup`，每分钟刷新编号和汇总，保留人工填写的业务预测、价格、状态和跟进记录。
日常刷新不再依赖原始订单提取文件或已退休表；只访问保留的业务表及私有状态/计数器。
刷新采用文件锁，失败不会重建已删除功能表，错误留在私有日志，最近成功时间另存JSON。
“当月概览”按上海月份自动切换；固定10月、11月及全部月份视图保留。
刷新保留后续人工调整的列宽与布局。不要用旧的全量导入器覆盖当前结构。

恢复时保留私有state、token、计数器和源快照；权限仅服务器用户可读。
计数器文件丢失时，可从备份中的地区市场保留上限和现有订单序号重建；不要手工降低上限。
Teable成员权限仍通过网站邀请管理，本次业务结构更新不改变任何账号权限。

跟进记录已按原链接及不可变源定位合并进订单，全文归档保留。
已取消：基地仓库、包装规格、提货退回单、交接单SKU行、履约分配、期初履约确认、订单数量变更、
数据核对、独立跟进记录、业务渠道、条码分配。源EAN文字仍保留。

七表精简另退休：业务大区、客户偏好关系表、产品标签关系表、分月计划、导入快照、原始台账行。
对应信息已合并，并非丢弃；见[迁移记录](../operations/2026-10-21-minimal-structure.md)。
